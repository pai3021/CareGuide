## 1. 改造前实现基线（main，保留用于对照）

- 外层采用意图路由，按需选择分诊、用药咨询、预约、升级角色。
- 普通角色被同时选中时，通过 `asyncio.gather()` 并发执行，再由编排器收集工具证据并汇总。
- 若识别结果带明确的 `agent_route`，优先采用该单角色路由；QIC 路径目前输出单角色。
- 四个角色之间没有基于中间结果的依赖调度；`primary_agent` / `supporting_agents` 不代表上下级委派。
- 接入模型时，专业角色内部采用受限的模型—工具—反馈循环，更接近 ReAct 式工具调用；没有明确复刻原论文的文本协议。未配置模型时走确定性工具回退。
- 尚未实现跨角色的 Planner、Plan-and-Execute 或通用 DAG 执行器，也未接入 LangGraph。
- 紧急情况优先选择升级角色，返回紧急就医提示；升级角色当前不等于通用人工交接执行器。
- 普通角色的并发业务查询是只读的。咨询交接记录、合成医院预约属于独立业务流程，可产生本地写入；预约变更须经用户确认后执行。
- 已有集中回复收口，主要按状态、工具消息和证据组织内容；尚未形成完整的异常分类、有限修正与统一用户反馈契约。
- 工具参数中的非法 JSON 当前会被归一为空字典再校验，可能将模型格式错误混同为用户缺少信息。
- 澄清目前主要依靠下一轮会话历史补全；会话历史、持久预约 action 与通用任务 checkpoint 是不同对象。
- 已有工具轮次上限、单次模型超时及重复调用控制，尚未形成覆盖整个工作流的累计预算与接近上限时的收尾机制。
- 启用持久记忆时，assistant 回复写入后触发画像提取；结构与来源校验、是否值得长期保存的判断及写入失败保护仍需完善。

## 2. 后续架构方向

采用分层设计：意图识别辅助理解，模型负责生成和更新任务计划，程序校验并调度执行；专业角色内层保留受限的 ReAct 式工具循环。支持首次动态规划和执行过程中的局部重规划，分阶段实施和验证。

```text
用户输入／后续补充 + 已有任务状态
    ↓
边界检查 + 意图识别辅助 + 任务分流
    ├─ 紧急情况 → 升级路径，停止普通任务调度
    ├─ 已核验的简单查询 → 直接路由 → 专业角色 → 结构化结果
    ├─ 已有任务补齐参数／确认 → 校验后恢复对应任务
    └─ 复合任务／依赖任务／需求变化 → Planner 生成计划或变更提案
                                            ↓
                              计划校验 + 结果／确认失效处理
                                            ↓
                                  按依赖调度 Agent 或工具
                                            ↓
                                      检查任务结果
                   ┌────────────────────────┼────────────────────┐
                   ↓                        ↓                    ↓
             继续就绪任务             需要用户信息／确认       需要调整计划
                   │                        ↓                    ↓
                   │                    暂停对应分支       有限次数回到 Planner
                   └────────────────────────┴────────────────────┘
                                            ↓
                              按任务汇总完成、待处理与失败结果
```

### 2.1 意图识别与模型规划的分工

- 意图识别提供候选业务意图、分数和边界信号；不能仅因分类器输出一个标签，就判定整句只有一个任务。
- Planner 同时读取完整用户原文、识别结果和已有任务状态，提出具体任务、动作、参数、依赖、输入引用和完成条件。识别结果作为辅助，不过滤原文中的其他需求。
- 后续输入需区分新增任务、补充参数、回答追问、修改需求、取消任务和确认操作；有歧义时追问，不自动修改已有操作。
- 边界检查独立于 Planner，规划和重规划均不能绕过急症优先、角色权限及预约确认规则。
- 简单查询保留直接路由，但分流策略须用多意图漏检样例验证；分别评测意图识别作为辅助后的收益和开销。
- 专业角色只完成指定子任务，通过结构化结果报告问题，不自行修改全局计划。一个角色可执行多个不同对象的任务，确定性业务动作可直接交给工具或业务服务。

### 2.2 两种动态与 DAG 的含义

- 首次动态规划：模型根据本次请求生成任务列表和依赖，例如 A 查医生、B 使用 A 的医生 ID 查号源、C 独立查药品资料；A 与 C 可并行，B 仅等待 A。
- 执行中动态重规划：模型结合执行结果或用户需求变化，提出新增、修改、取消任务的局部变更，经程序校验后生效。
- 每个生效版本的任务依赖须为 DAG。补参数后的同任务恢复、受限重试不必新增规划；需要改变任务目标、动作或依赖时才进入重规划。
- 外层“规划 → 执行 → 检查 → 再规划”允许循环，整个协调流程是有环状态图。
- 模型提出计划；动作白名单、权限、参数、依赖、预算、用户确认和实际执行由程序控制。
- A2A 是独立 Agent 应用间的互操作协议，当前不是本项目内部编排扩展的前置条件。

### 2.3 执行框架方向

- 优先评估并采用 LangGraph 承载外层流程，复用现有 Agent、工具、资料证据和预约服务；具体版本与持久化方案在实施前核对并确定。
- 固定“理解／规划／校验／调度／检查／汇总”的流程骨架，每个请求及计划版本中的任务与依赖可以动态变化。
- 任务 DAG 作为状态数据时，仍需显式实现就绪任务判断、输入绑定和局部失效规则；不假设框架会自动执行任意模型生成的计划。
- 自研执行器保留为成本比较与备选方案，比较重点为跨轮暂停、持久化恢复、动态分发和维护成本。

## 3. 后续实施清单

实施顺序建议：先固定基线与契约，优先完善异常分类和统一出口；将任务等待恢复、累计预算与 LangGraph 编排一起建设，避免重复实现；之后完善持久记忆写入。下列 P3.2—P3.5 对应一面暴露的四项改进；本轮实现及验证结果见勾选项与验收矩阵。P0/P4 的覆盖、延迟及调用量仅来自明确记录的离线小样例，不外推真实模型收益。

### P0：固定范围、分流策略与评测基线

- [x] 固定简单查询、跨角色独立查询、同角色多对象、跨任务依赖、缺参数、急症、执行中变更等样例。
- [x] 记录现有方案的任务覆盖率、完整完成率、证据正确性、工具调用、延迟与成本。
- [x] 评估现有 QIC 单标签输出的局限，定义意图识别作为辅助时的输入输出；单独统计复合请求误入简单路径的比例。
- [x] 明确直接路由、恢复已有任务和进入 Planner 的条件，不只依赖分类器的首选标签或分数。
- [x] 定义四个角色及确定性业务工作流的输入输出与权限，明确升级角色与人工交接工作流的关系。

### P1：定义任务计划、状态与结果契约

- [x] 定义计划 ID、版本、用户目标、任务 ID、原文片段、动作、执行角色／工具、参数、依赖、输入引用、预期输出和完成条件。
- [x] 定义任务状态与合法转换：等待依赖、就绪、执行中、成功、失败、需补充信息、待确认、依赖受阻、已取消和已失效；取消或失效时仍保留历史执行结果。
- [x] 定义请求级聚合状态和逐任务结果，区分全部完成、部分完成、等待用户和失败；不能仅因一个任务成功就将整句标为完成。
- [x] 以任务为单位隔离 entities、细粒度意图、动作及执行上下文，不沿用整句的单一全局动作。
- [x] 定义上游输出到下游参数的字段引用与类型校验；仅写 `depends_on` 不足以完成数据绑定。
- [x] 记录参数来自用户原文、历史确认、模型建议还是工具结果；模型建议和工具返回的候选项不等于用户选择或确认。
- [x] 校验动作／角色白名单、未知依赖、重复 ID、依赖环、输入引用、权限和计划规模；无效计划在有限修复后转为澄清或失败。
- [x] 定义单任务预算、请求总预算和跨轮预算的计数范围；暂停等待用户的时间与实际执行时间分别记录。

### P2：核定 LangGraph 集成与恢复方案

- [x] 核对现有依赖和 Python 兼容性，确定 LangGraph 版本及可回退的集成边界，不创建或更换主要运行环境。
- [x] 用最小工作流验证 State、条件路由、动态分发、依赖调度、汇合及分支暂停恢复，比较自研方案的维护成本。
- [x] 明确会话、计划版本和用户身份的绑定，选择持久化配置，验证并发请求不会相互覆盖状态。
- [x] 明确检查点恢复时哪些节点可能再次执行，将写操作隔离在现有受控业务服务中，沿用权限与幂等性校验。
- [x] 复用现有 `/actions/{identity}/confirm` 确认入口，明确业务确认状态与工作流恢复状态如何保持一致。
- [x] 保留现有直接路由的回归与回退能力；集成前完成选型和影响说明，确认后再迁移运行时。

### P3：接入首次规划与任务执行

- [x] Planner 输出结构化任务计划，读取用户原文及识别辅助信息；简单请求保留直接路由。
- [x] 将专业角色包装为接收明确子任务的 worker，返回任务 ID、状态、结构化数据、来源证据、缺失参数和错误信息。
- [x] 执行就绪任务；某任务依赖满足后立即启动，不等待无关任务；限制并发数，避免无限分发。
- [x] 检索绑定该任务的用户原文片段与已确认范围，保留可追溯关系；避免每个角色都对整句话检索。
- [x] 按任务及规范化参数去重工具调用，区分同一工具查询不同药品／医生的情况，不以工具名直接复用不同对象的结果。
- [x] 某分支缺少信息时仅暂停该分支，其他独立分支继续；上游失败时阻塞相关下游，保留其他已完成结果。
- [x] 将预约准备、用户选择、确认与执行分开，沿用并核对权限和幂等性约束。
- [x] 按任务汇总结果与证据，明确已完成、待补充、待确认、受阻和失败项；保留当前资料输出和医疗回答边界。

### P3.1：执行中局部重规划与计划变更

- [x] 定义事件及处理策略：缺参数优先追问并恢复；瞬时失败受限重试；无结果、持续失败、前提不成立或用户修改需求时评估是否重规划。
- [x] 重规划器读取当前版本、已执行结果、用户补充和触发原因，输出新增／修改／取消任务及其理由，不直接覆盖全部会话状态。
- [x] 所有变更在生效前执行与初始计划相同的校验，并核对基础计划版本，拒绝过期或冲突的变更。
- [x] 按参数、上游输入和用户目标的变化计算受影响任务及其下游；保留仍然有效的结果，失效并重新执行受影响任务。
- [x] 已执行写操作保留不可抹除的记录；修改计划不等于撤销预约，撤销或改期必须成为独立且重新确认的业务动作。
- [x] 用户更换科室、医生、日期、号源或操作类型时，废止受影响的旧选择与待确认操作；新参数重新准备、重新确认。无关只读任务变化不撤销有效确认。
- [x] 确认绑定用户、会话、具体动作及参数版本；确认入口校验操作是否仍有效，不能只依赖前端隐藏旧按钮。
- [x] 对正在执行的受影响任务设置取消或废止标记，旧版本的迟到结果不得写入新计划或解锁新任务；无法取消的写操作按实际执行结果对账。
- [x] 替换医院、日期、药品或扩大查询范围需用户授权；模型可提出备选方案，未经授权不自行切换。
- [x] 设置重规划次数、无进展次数、工具重试、总调用和执行时间上限；预算按工作流累计，不因改版或恢复而清零。
- [x] 达到上限后停止自动循环，汇总现有结果与未完成原因，必要时请求用户决定下一步。
- [x] Trace 记录计划版本、变更原因、任务增删改、失效传播、输入引用、结果版本、调用预算及写操作关联。

### P3.2：异常分类、有限修正与统一出口

- [x] 定义统一错误类型与结果契约，区分模型格式错误、用户缺少信息、参数业务校验失败、权限拒绝、资料未覆盖、工具／模型不可用和预算耗尽。
- [x] 错误结果记录任务 ID、调用 ID、错误码、发生阶段、是否可重试、缺失字段和面向用户的下一步；Trace 保存诊断信息，用户回复不暴露凭据或内部异常细节。
- [x] 模型工具参数无法解析时保留明确的解析失败状态，不直接以空字典替代并当成用户缺参；缺失信息的判断须结合原文和已有已确认参数。
- [x] 对格式或参数表达错误，允许预算内有限修正并重新校验；用户确实未提供必要信息时直接追问，权限拒绝等不可重试错误停止执行。
- [x] 修正失败后不猜测药品、医院、号源或写操作参数，不把最终自然语言回复重新当作可执行参数。
- [x] 在现有 composing 基础上形成统一出口：按任务呈现成功、部分完成、待补充、待确认和失败，保留有效证据及明确下一步。
- [x] 统一出口不更改业务真实状态，不将查询无结果说成工具故障，不将格式修正说成预约成功；不额外生成未经验证的医疗建议。
- [x] 优先提供确定性模板兜底，不为回复风格新增必需模型调用；若后续引入模型组织语言，另行确认范围并纳入预算，模型不可用时仍能返回标准结果。

### P3.3：任务等待、跨轮恢复与过期处理

- [x] 将等待协议纳入 P1 任务契约和 P2 LangGraph 恢复方案，复用现有会话与预约确认入口，不另建一套独立调度器。
- [x] 等待时保存工作流／任务 ID、用户与会话、计划版本、缺失字段、等待原因、已完成结果、输入引用、预算用量及过期时间。
- [x] 返回可理解的追问和必要选项，结束当前 HTTP 请求并释放执行资源；不靠长期占用连接等待用户填写。
- [x] 下一轮校验身份、会话、计划版本与回复所对应的任务；多个待回答问题无法唯一匹配时先澄清，防止补错分支。
- [x] 补齐参数后恢复对应任务，独立分支无需重跑；用户修改目标时转入 P3.1 局部重规划。
- [x] 分别定义会话记忆 TTL、等待任务有效期和预约确认有效期；用户未回复不等于授权自动选择或提交预约。
- [x] 等待过期后返回明确状态，按保留策略保留必要摘要供重新发起；旧确认不得直接恢复执行，清理范围与时机需可验证。
- [x] 恢复时重新检查号源等时效性信息及确认有效性；进程重启后仍能识别等待任务和已完成操作，并按实际结果对账。

### P3.4：累计预算、接近上限收尾与部分结果交付

- [x] 在现有模型／工具轮次限制上增加工作流累计模型调用、工具调用、重试、重规划及实际执行时间预算；记录可获得的 token 用量，并区分估算与实际统计。
- [x] 将单次请求执行期限、跨轮累计执行预算、任务有效期和等待用户时长分开定义；等待时停止不必要的执行，不靠恢复或改版重置累计用量。
- [x] 并发任务共享预算账本，在派发前预留额度，完成后结算；为收尾输出预留预算，避免多个分支同时检查通过后超额派发。
- [x] 接近上限时进入收尾阶段，停止非必要探索和新增分支，优先汇总已有证据、保存可恢复状态并说明剩余任务；硬上限仍由程序执行。
- [x] 达到上限时按真实结果返回部分完成或未完成，不将已成功查询全部丢弃；统一出口与格式修正也计入预算。
- [x] 区分协程取消与底层执行真正停止；核对同步线程、外部请求和迟到结果的处理，不能仅凭超时返回就宣称工作已经终止。
- [x] 已发出的写操作结果未知时先记录待核对状态，按幂等键或业务记录确认结果，不能因超时直接重发预约。
- [x] 保存预算耗尽原因、已用额度和恢复条件；用户选择继续也需程序检查额度，必要时明确授权增加预算，不无限自动续跑。

### P3.5：长期记忆写入门槛、来源与更新保护

- [x] 明确该项作用于启用持久记忆的配置；保留基础会话记忆路径，区分当前任务参数、会话历史和可跨会话复用的偏好。
- [x] 明确触发链：assistant 回复写入后的候选检查 → 必要时提取 → 结构及来源校验 → 合并更新；触发检查不等于每轮必须调用模型或写入画像。
- [x] 定义值得长期保存的门槛，例如用户明确表达的持续就医流程偏好；区分“以后优先上午的号”与“这次查上午的号”，没有合格候选时跳过写入。
- [x] 为画像及更新操作定义类型、字段白名单、长度和数量限制；每项候选关联用户原话或消息标识、时间、适用范围和版本。
- [x] 只依据用户明确表达的信息存储，不把助手建议、模型推断、检索资料或其他人的情况当作该用户事实；不由偏好提取推断诊断或风险。
- [x] 定义偏好去重、新旧冲突、明确更正和删除的规则；当前请求的明确要求优先于历史偏好，歧义不自动覆盖。
- [x] 更新失败保留旧画像，避免先删除旧数据再写入导致丢失；验证存储更新及版本冲突策略，同一用户并发会话不会静默覆盖更新。
- [x] 记忆提取和存储错误不阻塞已完成业务回复；为提取调用设置超时和独立可观测的预算，若采用异步写入需定义重试与去重。
- [x] 定义用户更正、删除、保留期限与清理方式，确保按用户隔离；Trace 记录必要来源标识和更新结果，避免复制无关敏感原文。

### P4：验证正确性与收益，再决定是否替换现有路径

- [x] 验证任务覆盖：跨角色多意图、同角色多对象均保留；分类器漏掉次要意图时，Planner 仍能根据原文拆出任务。
- [x] 验证依赖与数据绑定：下游读取指定版本的上游输出，未完成或已失效的数据不能启动下游；需要用户选择的候选项不能自动变成已确认参数。
- [x] 验证并发与部分完成：独立分支并行，下游仅等待自身依赖；单分支失败或追问不丢弃其他结果。
- [x] 验证计划校验、工具超时、失败传播、取消、过期变更和执行中旧结果迟到。
- [x] 验证第 4 节的全部重规划与跨轮案例，统计无效重规划、重复调用和预算耗尽情况。
- [x] 验证异常分类：非法 JSON、缺参、权限拒绝、资料未覆盖和服务故障进入不同分支；格式修正失败不触发猜参执行。
- [x] 验证等待用户时连接结束、状态持久化、回复绑定、不同 TTL 及过期后反馈，补信息后无需重跑独立分支。
- [x] 验证接近预算时收尾、并发预算预留、超限后的部分结果、恢复后累计预算及未知写操作结果核对。
- [x] 验证记忆无候选跳过、临时条件不固化、来源校验、冲突更正、删除、写入失败保旧及并发更新。
- [x] 验证急症优先、角色工具隔离、用户与会话隔离，普通规划及重规划均不能绕过边界。
- [x] 验证确认与失效：重复确认、修改参数后的旧确认、确认与修改并发、恢复后的重复提交，确保写操作按幂等约束执行。
- [x] 验证持久化后的跨轮确认、进程重启恢复及确认结果对账，不重新执行已完成写操作。
- [x] 与现有方案比较任务覆盖率、完整完成率、证据正确性、无关工具调用、延迟、调用次数与成本；单独报告简单请求开销和重规划场景结果。
- [x] 根据结果决定直接路由与规划路径的适用范围，保留回退方式，不预先宣称性能收益。

## 4. 示例依赖、变更规则与验收案例

以下流程已按验收矩阵验证；模型响应可控，医院操作限于当前合成医院范围。真实提供方评测另列为未验证。

### 4.1 首次动态规划

```text
A：查询已明确科室的医生 → B：用 A 的医生 ID 查询号源 → 用户选择号源
                                                               ↓
                                                           准备预约
                                                               ↓
                                                           用户确认
                                                               ↓
                                                         提交模拟预约
C：查询指定药品说明书（与 A 独立，可并行）

各分支按状态汇总；缺少参数的分支单独追问，不阻塞独立分支。
```

若用户要求查询所有返回医生的号源，B 可按医生分发；若用户要求指定医生，须先确认选择，不能将“候选医生”当作“已选医生”。用户是否需要预约由原始请求或后续明确指令决定。

### 4.2 动态重规划与恢复验收

| 场景 | 预期行为与验收重点 |
| --- | --- |
| 明天无号源，用户同意改查后天 | 告知无结果并提出备选；获得授权后更新日期和受影响任务，保留药品查询结果。 |
| 药品规格缺失，号源查询可执行 | 号源分支正常完成；药品分支追问，用户补齐后恢复，不重跑号源查询。 |
| 查询两个药品的禁忌 | 同一 MedicationAgent 可执行两个任务，分别绑定药品和证据，不因工具同名复用错误结果。 |
| 用户把消化内科改成心内科 | 失效旧医生、号源及相关待确认预约，重新查询；不使无关药品结果失效。 |
| 已准备预约后用户换号源，随后点击旧确认 | 后端拒绝旧操作，使用新参数重新准备和确认，旧号源不得被提交。 |
| 旧查询尚未返回时用户修改需求 | 旧结果仅留历史记录，不覆盖新计划、不触发下游执行。 |
| 号源服务暂时失败 | 预算内重试；持续失败后报告该分支失败或提出备选，正常药品查询仍交付。 |
| 无结果且模型连续提出相同计划 | 检测无进展并停止重规划，报告未完成原因，不无限消耗调用。 |
| 完成模拟预约后恢复、重规划或重复确认 | 对账并复用已完成操作记录，不重复创建；新改期／取消请求重新确认。 |
| 用户取消一个分支或新增一个查询 | 局部取消并传播至相关下游，或新增任务；保留仍有效的其他结果与确认。 |
| 后续输入出现当前急症风险 | 优先进入升级路径，停止普通任务调度，未执行预约写操作不再继续。 |
| 进程重启后用户补充或确认 | 恢复正确用户／会话的当前计划及预算，校验操作有效性，避免结果丢失和写操作重放。 |

验收重点是任务覆盖、真实的数据依赖、局部变更、合理并行及受控恢复，不要求每次调用全部四个角色。

### 4.3 一面反馈对应的可靠性验收

| 场景 | 预期行为与验收重点 |
| --- | --- |
| 用户已给足查询条件，模型返回非法 JSON | 识别为模型格式错误；预算内修正并重新校验，失败后停止对应执行，不要求用户重复补不存在的缺参。 |
| 用户确实没提供药品规格 | 返回明确缺失字段并等待补充，不让模型猜规格；已完成的号源结果保留。 |
| 一个查询成功，另一个工具超时 | 统一出口交付已完成资料及来源，准确说明失败项和下一步，不整句报成功或全部丢弃。 |
| 用户一直不回复，稍后或任务过期后返回 | 当前连接已释放；有效期内恢复，过期后明确告知并按规则重新发起，旧预约确认不可直接复用。 |
| 多分支同时接近预算，恢复后继续请求 | 预留额度防止超额派发，进入收尾并保存结果；恢复后沿用累计用量，不自动清零续跑。 |
| 预约接口超时但可能已经完成 | 标记结果待核对，先查业务记录或幂等结果，不直接重复提交或宣称失败后再次创建。 |
| 用户说“以后优先上午”，随后说“这次下午” | 持久偏好有用户来源；本次按下午查询，不自动覆盖长期偏好。用户明确更正时才更新。 |
| 提取无候选、JSON 不合法、画像存储失败或并发更新 | 无候选不写；非法提取不落库；失败保留旧画像和已完成回复；并发冲突可检测且有明确处理规则。 |

## 5. 面试表述边界

- 改造前：中心路由 + 普通角色并发查询 + 角色内部受限工具循环。
- 本轮已实现并离线验证：意图识别辅助 + 真实 Planner 接口首次规划／局部重规划 + 程序校验和 DAG 调度；LangGraph 承载外层循环，内层保留受限工具执行。
- 已完成的是代码能力、可控模型测试和现有服务集成；不将其表述为真实模型质量、临床能力、自主协作收益或线上性能收益。
- 任务恢复、预算、异常和画像按实际证据说明，已知限制、时效、索引兼容迁移及安全回退见实施记录。
