# Context 与 Memory 运行说明

## 存储职责

SQLite 保存获准留存的完整聊天原文、模型实际使用的工具调用及结果、累计摘要覆盖边界、请求重试记录，以及权威长期偏好。Redis 保存近期消息和当前摘要缓存。ChromaDB 保存历史摘要的语义索引。工作流执行事实仍由现有 WorkflowStore、ActionStore 和医院接口管理；LangGraph checkpoint 保存流程控制状态。

压缩不会删除 SQLite 原文，也不会把历史摘要升级为当前症状、医疗证据或业务成功凭据。用户偏好的正常写入不再依赖 ChromaDB；`CAREGUIDE_LEGACY_PROFILE_PROJECTION=1` 仅用于兼容旧双写行为。

## 启用与回退

默认仍为 `CAREGUIDE_MEMORY_MODE=session`，新归档、token 管理及周期复盘默认关闭；本次改造没有修改本机 `.env` 或重启服务。

要启用完整持久方案，在运行环境中设置：

```dotenv
CAREGUIDE_MEMORY_MODE=redis_chroma
CAREGUIDE_SESSION_ARCHIVE=1
CAREGUIDE_TOKEN_CONTEXT=1
CAREGUIDE_MEMORY_REVIEW_INTERVAL=10
CAREGUIDE_LEGACY_PROFILE_PROJECTION=0
```

SQLite 复用 `CAREGUIDE_BUSINESS_DB`，使用独立的 `memory_*` 表；偏好继续使用 `durable_profiles` 和 `profile_events`。Docker 已映射配置并使用现有业务持久卷。只需归档及恢复时可关闭 token 管理；`session` 加归档也支持重启恢复，但该模式没有偏好提取器或 Chroma 检索。周期偏好复盘需启用 `redis_chroma`。

关闭归档开关不会删除已有归档，但旧运行方式不会读取这些记录。关闭 token 管理会恢复原持久模式的消息条数压缩策略。新记录从开关启用后开始归档，无法恢复此前已过期、未保存的原文。

## 归档、重试与恢复

API 在执行前记录用户输入，执行成功后先归档最终回复，再更新缓存及偏好。请求失败时保留输入及失败状态。`POST /chat` 和 `/chat/stream` 可携带稳定的 `request_id` 作为调用方重试标识。归档开启后，已完成的相同请求直接返回已保存结果；相同标识配不同输入、未完成或失败的旧请求返回 409，不自动重新执行可能产生业务副作用的请求。

响应中的 `request_id` 继续表示原有追踪 ID；新增 `archive_request_id` 表示上述重试标识。重试应携带相同的用户身份、会话 ID 和归档请求标识。持久会话按服务端绑定的用户与会话联合隔离；公开部署应开启现有身份认证。

每轮从 SQLite 读取有效摘要及覆盖边界之后的消息，而不是依赖 Redis 一定存在。Redis 缺失时重建缓存；Redis 写入失败仍可使用已归档历史。SQLite 历史读取失败时停止本次处理，避免带着空历史误续任务。未完成请求保留为待检查记录，不自动重放；恢复工作流仍走既有版本和业务状态校验。

归档内工具记录只用于历史定位，不作为新的用户请求加入对话。完整历史查询可通过受用户与会话约束的 `SessionStore.messages()` 读取；本轮没有新增 `session_search` Agent 工具或 FTS5 检索。

## Token 预算与四阶段压缩

输入额度取应用输入上限与模型窗口扣除输出预留、安全余量后的较小值。默认配置是窗口 32768、输入上限 24000、输出预留 2048、余量 1024；这只是配置默认值，不代表自动探测了供应商窗口。可用 `CAREGUIDE_CONTEXT_MODEL_WINDOWS` JSON 按精确模型名设置实际窗口。预算配置必须与实际模型一致。

压缩触发比例为 0.85，目标比例为 0.60。最近窗口按 token 选择，不固定保留五条。完整请求检查覆盖系统指令、工具定义、偏好、检索背景、消息和工具结果，也覆盖回答流式调用。相同模型、工具和前缀下使用真实 usage 锚点加新增消息估算；没有锚点或请求结构改变时使用 UTF-8 启发式估算，不能视为精确分词或计费数据。

1. 确定性精简旧工具输出，保留调用标识及归档原文。保护当前用户请求和仍需消费的工具轮次。
2. 按 token 预算划分固定指令、待摘要历史和近期窗口，工具调用与结果成组保留。
3. 一次 LLM 调用更新结构化摘要，包含目标、约束、关键实体、已确认决策、未解决问题及来源；已有摘要作为更新输入的一部分。
4. 重新组装并检查最终额度、消息顺序和工具配对。来源范围由程序记录，不依赖模型猜测消息 ID。

摘要模型超时、输出截断、格式无效或没有有效缩减时保留原文和原上下文。软阈值内可以继续原请求；硬额度外停止该模型调用，由调用方现有错误/降级机制处理。压缩失败冷却时间持久化，防止重启后立即重复失败。超出摘要模型窗口的历史拒绝整段发送，不静默采样或删除中间原文。特别长的存量会话仍可能需要未来的分批摘要恢复策略。

摘要调用有超时，并通过独立 BudgetLedger 记录，单用户每天最多 100 次，避免隐藏在主模型调用内部而漏记。预算及失败统计保存在 SQLite。摘要与覆盖边界一起提交；Chroma 索引使用 SQLite 待处理队列和固定文档 ID，可在后续读取时重试，同一片段不会因重试不断产生新 ID。队列中保存的是具有原文范围的滚动摘要快照，不是完整原文副本。

## 长期偏好复盘

明确长期偏好、修改及删除仍在回复后及时检查。候选必须通过既有长期性规则、字段白名单和原文校验；临时安排、临床推断、第三方偏好和助手推断不自动写入。

可配置每 N 个已完成用户轮次触发后台增量复盘，10 是建议起点，0 为关闭。内部工具迭代不增加轮数。复盘读取上次边界之后的归档用户消息，单批输入估算上限 6000 tokens、超时 15 秒；规则无候选时不调用模型。复用既有偏好提取器和每日预算，不授予后台复盘任何医院操作权限。

计数和已处理边界持久化；后台失败不阻塞当前回复。正常关闭时对本进程访问过的短会话尝试收尾，最多等待五秒；进程被强杀不会保证立即提取，未推进的边界供后续轮次重试。SQLite 保存字段级来源顺序，包括已删除偏好的顺序标记，旧复盘无法覆盖较新来源或复活删除项。

## 旧画像检查

```bash
python -m scripts.audit_legacy_profiles --profile-db data/runtime/medical.sqlite3
python -m scripts.audit_legacy_profiles --profile-db data/runtime/medical.sqlite3 --prefix careguide_semantic
```

该工具只读并输出计数，不暴露画像内容，不创建或删除集合。当前本机服务检查到 `careguide_user_profile` 不存在，`careguide_semantic_user_profile` 有五条没有对应 SQLite 主记录的旧格式记录。它们仍原样保留，未被自动提升为已验证偏好；旧自由文本不能绕过现在的来源校验。迁移时应重新确认明确偏好，再走当前提取流程；确认无需旧记录后另行清理集合。本轮没有删除已有画像。

## 验证与结果边界

```bash
python -m pytest tests -q --basetemp=tmp/context-memory-tests
python -m scripts.benchmark_context_memory --output tmp/context-memory-new-report.json --real-services
```

对照脚本固定同一份 30 轮合成输入，比较进程内模式、旧条数摘要模式和新方案。比较阶段关闭情景检索以隔离压缩行为；其中旧模式缓存丢失后上下文为空的结果，不能解释为旧 ChromaDB 完全无法检索历史。模型输出使用明确标注的固定夹具，token 为估算值，耗时是夹具及存储流程耗时。真实 Redis/Chroma 检查也使用合成测试向量；运行时生成独立命名空间并清理，不操作医院数据或已有用户集合。

结果见 [对照记录](evaluation/context-memory-control-20261027.json)。当前结果证明原文留存、缓存丢失后恢复和压缩控制链路可运行；不证明自然语言摘要质量、临床有效性或真实线上时延。新方案相对旧摘要模式并未降低本场景估算输入 token，因此不宣称总体 token 节省或任务成功率提升。真实模型摘要保真度、多进程压力、保留期限与删除管理仍需后续评测和设计。
