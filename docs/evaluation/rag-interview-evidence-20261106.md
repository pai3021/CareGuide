# CareGuide RAG 面试证据与取舍

本文围绕当前代码和实际评测结果解释工作，不把开发实验、历史冻结结果和回答质量混成一个数字。

## 先讲清楚项目做到了什么

CareGuide 的 RAG 主链路包含范围与有效期过滤、Dense/BM25 召回、RRF 融合、候选池截断、可选专用重排和来源证据返回。检索层输出证据，后续回答由上层流程生成；检索命中率不是医疗回答准确率。

可以这样开场：

> 我在现有 RAG 链路上补了可复算的分阶段评测，比较过融合、候选池和 BGE-M3 稀疏召回。优化过程中，我没有只看一个最终分数，而是核对相关文档丢在哪一阶段，再用同样的候选预算和样本比较质量、Token 与耗时。收益不足的方案保留实验入口，没有直接替换默认配置。

代码证据：`careguide/retrieval/knowledge_base.py`、`score_fusion.py`、`reranker.py`，以及 `scripts/evaluate_rag_candidate_pools.py`、`analyze_rag_failures.py`、`compare_rag_rerank_models.py`。

## 数字如何对应

| 结果来源 | 样本与阶段 | 可说的结论 |
| --- | --- | --- |
| 历史冻结评测 | 1,000 条冻结 test，重排后 | Recall@10=66.8%、MRR@10=0.4857；这是保留的历史结果 |

| 实际重排候选池对照 | 固定100条开发验证 query | Top20最终命中58%，Top40最终命中60%，输入Token约1.98倍 |
| 真实 BGE-M3 Sparse 对照 | 相同500条内部验证，重排前 | 相比两路Min-Max，Top20覆盖+1.6个百分点、Recall@10仅+0.2个百分点 |
| 重排模型对照 | 同一100条开发query、英文指令、Top40 | 0.6B→4B最终Recall@10由60%到72%，MRR由0.4179到0.4656；Top100降至69% |
| Embedding模型对照 | 相同1024维、融合与4B重排器 | 500条内部验证Top40覆盖80.0%→83.6%；固定100条最终Recall@10仍为72% |

这些不是同一项实验的前后变化。历史 test 不参与本轮调参，100条试验子集也不当作新的独立测试。

## 高频追问与可核对回答

**“66.8%是不是很低？”**

目前效果仍有不足，不能称为高质量召回。我会说明这是约一万篇文档、单gold契约下的检索指标，并给出损失分解，而不是把数据难度当作效果好的证据。冻结评测中714条gold进了Top20，668条进了最终Top10，主要损失先发生在候选覆盖阶段；新的开发对照又显示，扩池之后重排损失也明显增加。

**“为什么要同时用Dense和BM25？”**

两者提供不同信号：Dense依赖语义表示，BM25依赖词项匹配。但互补性需要实测。500条内部验证中，Dense Top100覆盖86.0%，两路并集88.4%，确实补充了候选；压到Top20之后，两路RRF覆盖70.2%，反而低于Dense单路的71.2%，说明当前融合也会挤掉候选，不能只因使用混合检索就宣称更好。

**“为什么4:1，为什么RRF常数60？”**

这是被保留的开发基线参数，不是业务置信度。RRF按排名而非原始分数融合，避免直接混加余弦相似度和BM25不同量纲的分数。本轮验证了常数10/30/60和不同权重，Top40调参方案在验证半集反而低于原配置，因此没有用调参集最优代替验证结论。

**“为什么不直接把候选池设到100？”**

更大候选池提高覆盖上限，也增加重排输入和干扰项。已有真实对照中Top20到Top40的输入Token近乎翻倍，最终只净多命中2条；因此我先比较质量与成本。后续保持英文指令和4B模型不变比较Top100，最终命中由72%降到69%，没有采用。

**“为什么候选覆盖80%，最后只有60%？”**

同一100条样本中，Top40覆盖80条gold，但20条仍被排在最终Top10之外。新增覆盖的13条只有3条进入Top10，且原本命中的1条丢失。因此扩池收益没有被重排充分利用，需要固定候选池比较模型，而不能直接把80%写成最终效果。

后续固定英文指令和Top40，换成4B后命中72条，入池后漏掉的gold由20条降为8条。新增命中12条、丢失0条，配对差值区间[+6,+18]个百分点，因此提供4B Top40的质量优先配置。再扩大至Top100后命中降到69条、Token为2.48倍，这个配置不采用。完整记录见 [模型对照](rag-reranker-models-dev-20261106.md)。

**“为什么没有采用BGE-M3？”**

已经实测真实Sparse路径，不是用Dense向量或BM25冒充。它提供了补充候选，但相同验证集上相对两路Min-Max的Recall@10仅增加0.2个百分点，同时增加模型、编码和索引成本，所以保留为可选实验路径。Sparse编码的数值核对与整体检索质量分别验证。

**“为什么不把Embedding也换大？”**

已经固定1024维、检索指令、BM25、RRF及4B重排器，重新编码同一万篇语料和一千条开发query做过对照。500条内部验证Top40覆盖从80.0%升至83.6%；同一100条试验子集覆盖从80%升至85%，但最终Recall@10仍为72%，新增4条、丢失4条，MRR还略降。因此我把结论限定为候选覆盖改善，保留独立4B索引，暂不替换0.6B Embedding。下一步先查候选入池后为何未命中，不能直接把更大模型等同于最终效果更好。见[Embedding对照及零API复算](rag-embedding4b-dev-20261106.md)。

**“除了换模型，还实际试过什么？”**

还测试过中文n-gram分词、BM25长度归一、各路候选保留配额和MMR去冗余。加入单字后，500条内部验证的BM25 Top100覆盖从57.6%到71.6%，两路并集从91.0%到92.8%，但固定融合压到Top40后覆盖略降；去冗余也没有增加最终命中。因此我把候选收益与整条链路收益分别报告，保留可复算实验，没有直接改默认策略。见[后续优化记录](rag-target80-offline-dev-20261106.md)。

还用同一批已缓存向量比较过ANN与精确余弦搜索，排除了重新编码因素：500条内部验证Dense Top100覆盖89.4%→91.0%，融合Top40覆盖83.6%→84.4%。提供了先过滤范围和有效期的可选精确检索入口，但尚未把候选收益写成重排后的最终提升。

后续还做了200次真实请求的Top80、检索指令与8B对照。8B在调参50条上Top1更好，Recall@10反而较低；按预定规则选出的4B Top80在内部验证50条从70%降到64%，完整100条从72%降到68%，因此不采用。这个结果支持“不能只靠扩池和换大模型”的取舍，不支持已经超过80%的说法。见[真实对照](rag-target80-rerank-dev-20261106.md)。

**“你说gold可能不完整，是不是在替低分找理由？”**

原评分始终保留，没有删除难例或改变冻结test。我记录了可复核的文本现象，例如query问症状而gold主要讲治疗，query引用图片但输入没有图片。这样的案例说明单gold命中与实际相关性需要分开评估。若补充人工多相关标注，应另建版本、固定标准，单独报告，不能替换原结果制造提升。

**“怎么防止数据泄漏？”**

构建脚本按唯一gold文档拆分train/dev/test，索引正文不放被标注的query，KUAKE标题是通用标题而非问题复写。评测脚本校验语料、样本、分数缓存身份；gold只在离线计算指标和损失追踪时使用，不进入检索特征或重排请求。冻结test不反复用于选权重和模型。

**“统计上怎么证明提升？”**

比较同一批query的配对结果，同时报告新增命中和丢失命中。100条试验中Top40净增2条，配对bootstrap的Recall差值95%区间是[-2,+6]个百分点，所以当时没有宣称稳定提升。开发数据曾参与方案选择，结论也应限定为开发实验。

**“你说延迟改善，是线上P95吗？”**

本轮记录的是独立Rerank API调用耗时，包含客户端请求开销，不包括检索、编排、回答生成和生产并发排队，不能叫完整服务P95。输入Token来自API返回的usage，费用还应以实际账户账单核对。

## 面试时保留的判断

结果有不足就直接承认，然后用损失分解说明下一步。可以突出三个具体能力：把最终指标拆到阶段、用单变量对照检验解释、根据质量与成本决定是否采用方案。本轮72%是同一100条开发子集的实测结果，尚未达到最终80%，也不把它当作新的冻结测试成绩。
